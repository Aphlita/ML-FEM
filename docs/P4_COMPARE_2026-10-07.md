# P4 防护效果复测与性能开销（三组对照实验）

对应竞赛题目要求 7（防护效果验证）与要求 8（性能要求）。
参数集 ML-KEM-512，2026-10-07 于服务器 `pc12-ThinkStation-P920` 采集。

## 1 实验目的

用一个明确标注为对照的可变时间实现，验证下面这条完整闭环成立：

```text
平台能检出差异  ->  修复后差异消失  ->  修复没有引入性能开销
```

这里测的是**平台对实现差异的检测与复测能力**，不是"ML-KEM 本身有漏洞"。
规范实现（基线）检不出差异是合理结果，不是失败。

## 2 三个被测目标

| 目标 | 角色 | 说明 |
|---|---|---|
| `mlkem_native_baseline` | 基线 | 平台默认的 mlkem-native 规范实现，库在 `backend/lib/` |
| `variant_early_return` | 对照 | 含提前返回式比较的对照实现，用于证明平台能发现明显差异 |
| `variant_fixed` | 修复 | 改为固定流程的修复实现，语义不变，用于前后对比 |

> **前置说明**：`targets/` 目录及其 `build.sh` 目前在服务器工作区里，**尚未提交到仓库**。
> 本报告的原始 CSV 保存在服务器 `results/p4_compare/`（该目录已被 `.gitignore` 忽略）。
> 基线目标的库路径与另外两个不同（`backend/lib/` 而非 `targets/<id>/lib/`），
> 复现脚本里已做映射。

| 项目 | 取值 |

| 主机 | pc12-ThinkStation-P920 |
| CPU | Intel(R) Xeon(R) Gold 6234 @ 3.30GHz，2 路共 32 线程 |
| 内核 | 5.4.0-216-generic |
| 固定 CPU 核 | 0（`taskset -c 0`） |
| 频率策略 | `powersave`（未修改，如实记录） |
| 每轮配对数 | 20000 |
| 轮数 | 5 |
| 计时方式 | `CLOCK_MONOTONIC_RAW`，只包住 `mlkem_dec` 调用；预热由计时程序内部完成 |
| 采样顺序 | **三个目标轮转交叉**，抵消频率/温度漂移 |

## 4 结果（两次独立运行）

### 4.1 检测能力

差值定义为「变化输入 − 正常输入」，单位为纳秒。每轮都做配对分析：
对时间块均值做单样本 t 检验与 Wilcoxon 符号秩检验，块大小为 200 组。

**第一次运行**

| 目标 | 五轮块平衡均值差（ns） | 平均 | 检出 |
|---|---|---|---|
| 平台基线实现 | +2.59 / −7.83 / +2.65 / −2.18 / +9.14 | **+0.87** | **0/5** |
| 对照实现（早退比较） | −276.42 / −271.96 / −212.89 / −264.93 / −285.86 | **−262.41** | **5/5** |
| 修复实现（固定流程） | −3.85 / +4.51 / +24.60 / +5.59 / −4.08 | **+5.35** | **0/5** |

**第二次运行（独立重跑，同参数）**

| 目标 | 五轮块平衡均值差（ns） | 平均 | 检出 |
|---|---|---|---|
| 平台基线实现 | +1.50 / −4.82 / +3.05 / +3.22 / +8.95 | **+2.38** | **0/5** |
| 对照实现（早退比较） | −268.98 / −283.38 / −265.81 / −268.43 / −270.56 | **−271.43** | **5/5** |
| 修复实现（固定流程） | −20.88 / −9.61 / −3.60 / +0.94 / −6.68 | **−7.97** | **0/5** |

对照实现的显著性水平极高（配对 t 检验 p 值在 1e-70 到 1e-90 量级，
Wilcoxon p = 3.96e-18），95% 置信区间在每一轮都明显不含零。

## 5 结论

1. **平台能稳定发现对照实现的差异。** 两次独立运行都是 5/5 轮全部检出，
   差值分别为 −262.4 ns 与 −271.4 ns，量级一致（相差 3%）。
2. **修复后差异降到检不出的水平。** 修复实现两次都是 0/5 轮检出，
   平均差值 +5.4 ns 与 −8.0 ns，95% 置信区间均跨零。
3. **修复没有引入可测的性能开销。** 修复实现相对基线为 −0.10% 与 −0.87%，
   两次都落在 ±1% 以内，而基线本身的轮间漂移就有约 1%（30981 → 31301 ns）。
   因此准确说法是"修复与基线处于同一水平"，**不能声称修复更快**。
4. **一个稳定复现的观察：早退比较版本的耗时波动明显更大。**
   对照实现的标准差为 1237 / 1512 ns，而基线是 715 / 604 ns，修复实现是 608 / 1649 ns。
   提前返回让执行路径长度随输入变化，这一点在两次运行中方向一致，
   也从侧面说明差异的来源确实是执行路径而不是单纯的测量噪声。

## 6 需要注意的边界

- 本文的结论只对**本次环境与本次输入类别**成立。`powersave` 频率策略下
  绝对耗时在不同轮次之间会漂移约 1%，所以性能开销只能按"同一量级"表述。
- 修复实现仍偶有波动较大的轮次：第一次运行第 3 轮为 +24.60 ns
  （区间 [−20.08, +69.29]），第二次运行整体标准差达 1648.9 ns。
  这属于测量噪声，不应据此认为修复不彻底，但也说明**多轮重复是必要的**。
- **未检出差异不能证明实现绝对恒定时间**，只说明在本次样本量与输入类别下没测出来。
- 对照实现是专门准备的演示目标，**不代表 mlkem-native 的实现质量**。
- 本实验用的是「正常密文 vs 翻转一位密文」。这个对比能测出**执行路径长度变化**
  引起的差异（对照实现的情形），但**测不出编译器引入的、只依赖消息位分布的分支差异**——
  因为两类密文解出的消息都近似均匀随机，置位数均值相同，平均差会相互抵消。
  后者需要精心构造的稀疏密文（见 `experiments/clangover-poc/`）。

## 7 复现方式

```bash
# 在服务器项目根目录下
bash experiments/p4_compare/run_compare.sh          # 轮转交叉采样，约 40 秒
python3 experiments/p4_compare/summarize_compare.py # 输出表 1～3 与环境信息
```

可用环境变量覆盖默认参数：`P4_ROUNDS`、`P4_PAIRS`、`P4_CPU`。

原始数据：`results/p4_compare/<目标>-r<轮>.csv`（每行一个配对，含先后顺序），
环境快照：`results/p4_compare/env.txt`。

分析口径全部来自 `backend/stats.py`：块平衡配对估计 + 单样本 t 检验 +
Wilcoxon 符号秩检验；独立样本 Welch / Mann-Whitney 仅作参考，不参与判定。
